## ЧАСТЬ 1. Правила формирования проводок (Актив / Пассив и Дебет / Кредит)
В банковском учете (согласно Положению Банка России № 809-П) жестко действует бухгалтерское правило двойной записи. Поведение счетов зависит от их типа: Активный (А), Пассивный (П) или Активно-Пассивный (А-П) (в основном, счета учета финансовых результатов или парные счета).
## Матрица движений по счетам:

* Активные счета (ссудные счета клиентов, корсчета в ЦБ, касса):
* Дебет (Дт) ➡️ Увеличение актива (выдали новый кредит, приехали наличные в кассу).
   * Кредит (Кт) ➡️ Уменьшение актива (клиент частично погасил долг перед банком, списали деньги с корсчета).
* Пассивные счета (расчетные счета юрлиц, вклады физлиц, собственный капитал банка):
* Дебет (Дт) ➡️ Уменьшение пассива (клиент перевел деньги в другой банк, банк вернул вклад).
   * Кредит (Кт) ➡️ Увеличение пассива (клиенту пришла зарплата, открыт новый депозит).

## Как заложить эти правила в онтологию (SHACL / Валидация)
Поскольку OBDA работает в режиме «чтения», проверять эти правила на этапе вставки транзакции в реляционную БД должен код АБС. Однако семантический слой используется для аудита и выявления аномалий.
Чтобы Triple Store автоматически находил ошибочные проводки, мы пишем логические правила (например, на языке SHACL или через SPIN/SWRL rules).
## Пример логического контроля в графе:

«Если проводка уменьшает Активный счет, этот счет должен быть строго в Кредите. Если проводка увеличивает Пассивный счет, он должен быть в Кредите».

Если в реляционной БД из-за бага АБС пройдет операция, нарушающая баланс (например, пассивный счет уйдет в несанкционированный минус), граф при аудите моментально подсветит этот узел как InvalidTransaction.

## ЧАСТЬ 2. Формат записи: Почему TriG лучше для банковских транзакций
Использование чистого Turtle имеет огромный недостаток для банковского домена: Turtle описывает плоский граф, где все триплеты валятся в одну «кучу» (Default Graph).
В реальной жизни проводка редко существует сама по себе. Банковская Транзакция (Документ) — это атомарный пакет, который может содержать:

   1. Основную проводку (перевод 10 000 руб.).
   2. Связанную проводку (удержание комиссии 100 руб.).
   3. Техническую проводку (НДС с комиссии).

Если одна из этих проводок отвалится, вся транзакция должна откатиться.
## Решение: Формат TriG и Именованные Графы (Named Graphs)
Формат TriG (расширение Turtle) позволяет группировать триплеты в Именованные Графы с помощью фигурных скобок {}.
Это идеальное решение для банковского учета по трем причинам:

   1. Атомарность транзакции: Весь пакет проводок оборачивается в один граф, имеющий URI транзакции.
   2. Аудит и Метаданные (Происхождение данных / Provenance): Мы можем привязать метаданные (кто провел, в какой АБС, во сколько, электронная подпись) не к каждой отдельной проводке, а к графу транзакции целиком.
   3. Версионирование (Сторнирование): Если транзакцию нужно отменить (засторнировать), в TriG мы можем пометить старый граф транзакции как ex:status ex:Deprecated, не ломая историю.

## Пример записи банковского документа в формате TriG
Ниже показано, как в рамках одного документа (транзакции перевода с комиссией) инкапсулировать несколько проводок, связав их с метаданными.
```
@prefix rbo: <http://example.com> .
@prefix ex:  <http://example.com> .
@prefix xsd: <http://w3.org> .

# =================================================================
# МЕТАДАННЫЕ ТРАНЗАКЦИИ (Лежат в дефолтном графе)
# =================================================================
ex:PaymentContext_Tx999888 a rbo:BankTransaction ;
    rbo:transactionId "TX-999888" ;
    rbo:operatorId "user_abs_front_04" ;
    rbo:systemSource "Retail_Core_Active" ;
    rbo:executionStatus rbo:StatusSuccess ;
    # Связываем метаданные с конкретным именованным графом
    rbo:hasPayloadGraph ex:TransactionGraph_Tx999888 .


# =================================================================
# ИМЕНОВАННЫЙ ГРАФ: Пакет проводок (Атомарный контейнер)
# =================================================================
ex:TransactionGraph_Tx999888 {

    # Проводка №1: Основной перевод (Уменьшение пассива клиента А -> Увеличение пассива клиента Б)
    ex:Entry_Main a rbo:AccountingEntry ;
        rbo:hasDebitAccount  ex:Acc_ClientA_40817 ;  # Пассивный счет (Дт = Уменьшение)
        rbo:hasCreditAccount ex:Acc_ClientB_40817 ;  # Пассивный счет (Кт = Увеличение)
        rbo:amountValue      "10000.00"^^xsd:decimal ;
        rbo:currencyNumCode  "643" ;
        rbo:bookingTimestamp "2026-08-27T15:30:00Z"^^xsd:dateTime .

    # Проводка №2: Удержание комиссии банком (Уменьшение пассива клиента А -> Увеличение дохода банка)
    ex:Entry_Commission a rbo:AccountingEntry ;
        rbo:hasDebitAccount  ex:Acc_ClientA_40817 ;  # Пассивный счет клиента (Дт = Уменьшение)
        rbo:hasCreditAccount ex:Acc_BankIncome_70601 ; # Пассивный счет доходов банка (Кт = Увеличение)
        rbo:amountValue      "100.00"^^xsd:decimal ;
        rbo:currencyNumCode  "643" ;
        rbo:bookingTimestamp "2026-08-27T15:30:00Z"^^xsd:dateTime .
}
```

## 🚀 Как это помогает при сборке отчетности в Triple Store?
Если вы используете TriG и Named Graphs, ваши SPARQL-запросы становятся гораздо мощнее. Вы можете анализировать данные на уровне бизнес-контекста:

* Запрос на выявление фрода/ошибок: Вы можете написать запрос, который проверяет: «Найди мне такие транзакции (графы), где сумма всех дебетов не равна сумме всех кредитов внутри этого конкретного графа».
* Выборочный аудит: Вы можете мгновенно отсечь технические проводки и запросить баланс только по графам, которые пришли из определенной системы-источника (rbo:systemSource "Retail_Core_Active").

Если этот подход вам подходит, мы можем сделать следующий шаг. Скажите:

* Интересно ли вам посмотреть пример SPARQL-запроса, работающего с Named Graphs (TriG) для проверки баланса внутри одной транзакции?
* Стоит ли добавить в модель классы для парных счетов (которые в зависимости от сальдо могут становиться либо активными, либо пассивными в конце операционного дня)?

## 2
В онтологии нужно учесть:
```
У транзакций обычно есть как минимум две, иногда три временных метки:

Момент валютирования. Когда произошла транзакция.

Момент проводки. Время записи транзакции в системе.

Момент расчёта. Время реального перевода или материализации средств. Он есть не у каждой транзакции. Обычно выражается в виде T+X, где X — количество дней после валютирования, когда происходит расчёт (например, T+2 означает через 2 дня после валютирования).
```

Вы абсолютно правы. В банковском учете и международном финтехе разделение временных меток — это критически важный аспект. Без него невозможно корректно рассчитать ликвидность на конкретную дату, построить отчетность по рискам или смоделировать биржевые сделки.
В семантических стандартах (включая FIBO) эти понятия строго разграничены, так как они отражают разные стадии жизненного цикла транзакции: юридическую, учетную и финансовую.
Ниже приведено описание этих меток применительно к банковской онтологии и расширенная схема в формате TriG, учитывающая эти концепты.

------------------------------
## 🕒 Разбор трех временных меток в банкинге

   1. Дата валютирования (Value Date / Т)
   * Суть: День, начиная с которого начисленные на сумму транзакции проценты начинают учитываться в балансе, или дата вступления в силу экономических прав по сделке.
      * Пример: Вы совершили покупку по карте за рубежом в субботу. Деньги заблокированы. Дата валютирования для вас — суббота (момент совершения операции).
   2. Дата проводки / Отражения в учете (Booking Date / Posting Date)
   * Суть: Время, когда бухгалтерская система (АБС) фактически создала проводку по счетам дебета и кредита и закрыла операционный день.
      * Пример: Из-за выходных дней или времени обработки реестров клиринга, банк спишет деньги по субботней покупке только в понедельник утром. Понедельник — это дата проводки.
   3. Дата расчета / Сеттлмента (Settlement Date / T+X)
   * Суть: Дата окончательного межбанковского расчета (например, через платежную систему Центробанка или клиринговый центр), когда реальные деньги физически перешли с корсчета одного банка на корсчет другого.
      * Специфика (T+X): На рынках ценных бумаг или при конвертации валют (FX) сделка заключается сегодня, а реальная поставка активов происходит через 1–2 рабочих дня (T+1, T+2). До этого момента у банка возникает временное обязательство (дебиторская/кредиторская задолженность).

## 🛠️ Расширение схемы онтологии в формате TriG
Добавим эти свойства данных (Data Properties) и правила в структуру нашей онтологии. Мы будем использовать формат TriG, чтобы инкапсулировать метаданные транзакции.
```
@prefix rbo:  <http://example.com> .
@prefix ex:   <http://example.com> .
@prefix xsd:  <http://w3.org> .
@prefix owl:  <http://w3.org> .
@prefix rdfs: <http://w3.org> .

# =================================================================
# ДОПОЛНЕНИЕ К СХЕМЕ ОНТОЛОГИИ (Временные свойства)
# =================================================================
rbo:valueDate a owl:DatatypeProperty ;
    rdfs:domain [ a owl:Class ; owl:unionOf (rbo:AccountingEntry rbo:BankTransaction) ] ;
    rdfs:range xsd:date ;
    rdfs:label "Дата валютирования (Value Date)" ;
    rdfs:comment "Дата, с которой транзакция вступает в экономическую силу." .

rbo:bookingTimestamp a owl:DatatypeProperty ;
    rdfs:domain rbo:AccountingEntry ;
    rdfs:range xsd:dateTime ;
    rdfs:label "Время проводки (Booking Timestamp)" ;
    rdfs:comment "Физическое время записи транзакции в бухгалтерский леджер АБС." .

rbo:settlementDate a owl:DatatypeProperty ;
    rdfs:domain rbo:BankTransaction ;
    rdfs:range xsd:date ;
    rdfs:label "Дата окончательного расчета (Settlement Date)" ;
    rdfs:comment "Дата фактического движения средств на уровне межбанковского клиринга." .

rbo:settlementLag a owl:DatatypeProperty ;
    rdfs:domain rbo:BankTransaction ;
    rdfs:range xsd:string ;
    rdfs:label "Срок расчета (T+X)" ;
    rdfs:comment "Спецификация лага расчета, например: 'T+0', 'T+1', 'T+2'." .


# =================================================================
# ПРИМЕР ЗАПИСИ СЛОЖНОЙ СДЕЛКИ (Валютный своп/конвертация T+2)
# =================================================================

# Контекст транзакции в дефолтном графе
ex:FX_Trade_77665 a rbo:BankTransaction ;
    rbo:transactionId "FX-77665" ;
    rbo:valueDate "2026-08-27"^^xsd:date ;          # Сегодня совершили сделку (Т)
    rbo:settlementLag "T+2" ;                       # Условие: расчет через 2 дня
    rbo:settlementDate "2026-08-29"^^xsd:date ;      # Реальные деньги придут 29-го числа
    rbo:hasPayloadGraph ex:Payload_FX_77665 .

# Именованный граф с бухгалтерскими проводками
ex:Payload_FX_77665 {
    
    # Бухгалтер зафиксировал сделку в системе АБС в 22:45
    ex:Entry_USD_Debit a rbo:AccountingEntry ;
        rbo:hasDebitAccount  ex:Acc_Transit_USD ;
        rbo:hasCreditAccount ex:Acc_Client_USD ;
        rbo:amountValue      "1000.00"^^xsd:decimal ;
        rbo:currencyNumCode  "840" ;
        rbo:valueDate "2026-08-27"^^xsd:date ;
        rbo:bookingTimestamp "2026-08-27T22:45:00Z"^^xsd:dateTime . # Время фиксации в БД
}
```

## 📊 Зачем это разделение нужно при построении отчетности?
Имея такую семантическую разметку временных меток, вы можете решать сложнейшие задачи управления рисками с помощью простых SPARQL-запросов:

   1. Расчет «Грязного» и «Чистого» баланса (Liquidity Management):
   * Если вам нужен бухгалтерский баланс для регулятора на сегодня, вы фильтруете данные строго по rbo:bookingTimestamp (что фактически записано в книге).
      * Если вам нужен прогноз ликвидности (сколько реальных денег будет у банка через 2 дня), вы делаете выборку по rbo:settlementDate. Система учтет сделки T+2, которые еще не прошли по бухгалтерии, но юридически уже неизбежны.
   2. Анализ задержек (Operational Risk):
   * Можно автоматически находить транзакции, у которых разница между датой валютирования (valueDate) и датой проводки (bookingTimestamp) превышает допустимый лимит (например, более 1 дня). Это явный признак сбоя в очередях обработки платежей (платежном конвейере) или зависшего ностро-счета.

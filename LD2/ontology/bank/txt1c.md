## 1

RDF-star (RDF*) — это расширение стандарта RDF, разработанное специально для решения проблемы метамоделирования (утверждений об утверждениях). В классическом RDF триплет — это атомарная связь «Субъект-Предикат-Объект». Нельзя было просто так взять и сказать: «Эта проводка была создана в 15:30», потому что «создана в 15:30» — это свойство самой связи, а не счета или суммы.
В банковской сфере RDF-star производит революцию, так как позволяет вешать метаданные (временные метки, статусы, ЭЦП, аудиторский след) напрямую на каждую конкретную связь или проводку без раздувания графа.

------------------------------
## 📊 Сравнительная таблица подходов к моделированию транзакций

| Критерий сравнения | Классический RDF (Чистый Turtle) | Именованные графы (TriG) | Реификация (старый RDF W3C) | RDF-star (RDF*) |
|---|---|---|---|---|
| Суть подхода | Все триплеты в одной плоской куче. | Группировка триплетов в именованные контейнеры {}. | Создание специального технического узла (паспорта) для триплета. | Использование триплета в качестве Субъекта или Объекта внутри другого триплета. |
| Синтаксис | :s :p :o . | :GraphURI { :s :p :o } | :_id a rdf:Statement ; rdf:subject :s ... | <<:s :p :o>> :property :value . |
| Гранулярность метаданных | Нулевая. Нельзя разметить отдельный триплет. | Пакетная. Метаданные вешаются на весь граф (группу проводок). | Поштучная, но крайне громоздкая (1 связь превращается в 4-5 триплетов). | Поштучная. Идеальная точность для каждого отдельного атрибута или проводки. |
| Объем базы данных (раздувание) | Минимальный (нет метаданных). | Низкий (один URI графа на пакет проводок). | Критический. База данных вырастает в 4–5 раз, падает производительность. | Минимальный. База хранит компактные вложенные триплеты. |
| Удобство SPARQL-запросов | Простое. | Среднее (нужно постоянно использовать конструкцию GRAPH ?g { ... }). | Ужасное (запросы перегружены техническими rdf:subject, rdf:object). | Высокое (в SPARQL 1.1-star появились нативные конструкции <<...>>). |
| Идеальный юзкейс в банке | Простые справочники (БИК, Планы счетов, коды валют). | Банковский ордер/документ, содержащий цепочку связанных проводок. | Устарел. Не рекомендуется к использованию. | Аудиторский след, версионирование, временные метки (Value/Booking Date) для каждой связи. |

------------------------------
## 🛠️ Сравнительные примеры: Как записать временные метки транзакции
Давайте запишем одну и ту же банковскую сущность: «Счет Дебета для транзакции — Счет_А. Эта связь имеет Дату валютирования 2026-08-27 и добавлена оператором user01».
## 1. Вариант на RDF-star (Самый элегантный и современный)
В RDF-star вложенный триплет заключается в двойные угловые скобки << >>. Они показывают, что свойства valueDate и recordedBy относятся именно к факту назначения дебет-счета.
```
@prefix rbo: <http://example.com> .
@prefix ex:  <http://example.com> .
@prefix xsd: <http://w3.org> .

# Задаем проводку и вешаем метаданные прямо на её связи!
ex:Tx_10050 rbo:hasDebitAccount ex:Acc_Debit_40817 .

<< ex:Tx_10050 rbo:hasDebitAccount ex:Acc_Debit_40817 >> 
    rbo:valueDate "2026-08-27"^^xsd:date ;
    rbo:recordedBy "operator_user01" .

## 2. Вариант на TriG (Именованные графы)
Здесь мы вынуждены создать отдельный граф-контейнер для одной транзакции, а метаданные вешать на сам контейнер.

@prefix rbo: <http://example.com> .
@prefix ex:  <http://example.com> .
@prefix xsd: <http://w3.org> .

# Метаданные вешаются на граф целиком
ex:Graph_Tx_10050 {
    ex:Tx_10050 rbo:hasDebitAccount ex:Acc_Debit_40817 .
}

# В дефолтном графе описываем свойства этого контейнера
ex:Graph_Tx_10050 
    rbo:valueDate "2026-08-27"^^xsd:date ;
    rbo:recordedBy "operator_user01" .

## 3. Старый вариант: Классическая реификация (W3C Reification)
Посмотрите, в какой кошмар превращается запись без RDF-star и TriG. Чтобы описать одну связь, нам нужно создать технический узел ex:Statement_1 и четыре вспомогательных триплета.

@prefix rbo: <http://example.com> .
@prefix ex:  <http://example.com> .
@prefix rdf: <http://w3.org> .
@prefix xsd: <http://w3.org> .

# Описываем сам факт связи через технический объект
ex:Statement_1 a rdf:Statement ;
    rdf:subject   ex:Tx_10050 ;
    rdf:predicate rbo:hasDebitAccount ;
    rdf:object    ex:Acc_Debit_40817 ;
    # И только теперь вешаем метаданные
    rbo:valueDate "2026-08-27"^^xsd:date ;
    rbo:recordedBy "operator_user01" .
```

------------------------------
## 🚀 Главные преимущества RDF-star для банка

   1. Эффективное Сторнирование (Отмена проводок):
   Если АБС ошиблась и проводку нужно отменить, в RDF-star не нужно удалять данные или переписывать граф. Вы просто добавляете к ошибочной связи статус:
   << :Tx_1 :hasDebitAccount :Acc_A >> rbo:status "Canceled" .
   2. Точечный аудит (След происхождения данных — Provenance):
   При интеграции данных из разных АБС (например, одна часть данных пришла из ЦФТ, другая из Диасофта), вы можете пометить каждый конкретный факт источником его происхождения. Ризонер сможет отсекать сомнительные данные на лету.
   3. Совместимость с Property Graphs (Нео4ј):
   Раньше между миром семантического веба (RDF/W3C) и миром промышленных графовых БД (Neo4j, где у связей всегда есть свойства) была пропасть. RDF-star полностью сокращает этот разрыв. Вы можете строить OBDA-модели, которые прозрачно маппятся на графы со свойствами дуг.

## 🔍 Как это запрашивать? (Пример SPARQL-star)
Чтобы вытащить проводки, которые зафиксировал конкретный оператор, в SPARQL-star используется точно такой же вложенный синтаксис:
```
PREFIX rbo: <http://example.com>
PREFIX xsd: <http://w3.org>

SELECT ?tx ?account ?vDate
WHERE {
   # Ищем вложенный триплет, у которого есть метасвойство оператора
   << ?tx rbo:hasDebitAccount ?account >> rbo:recordedBy "operator_user01" ;
                                          rbo:valueDate ?vDate .
}
```

## 2

Для решения задачи автоматической сборки Оборотно-сальдовой ведомости (Форма 101) для Банка России мы объединим все рассмотренные технологии в сквозной архитектурный пайплайн.
Форма 101 — это критически важный надзорный документ, который требует расчета входящих остатков, оборотов по дебету и кредиту, а также исходящих остатков за отчетный период (обычно месяц) в разрезе балансовых счетов второго порядка (5 знаков) и валют.
Ниже представлен детальный проект реализации Формы 101 с использованием гибридного подхода OBDA + RDF-star.

------------------------------
## 🗺️ Сквозная архитектура решения

 [ Реляционная БД / СУБД ] ──( Маппинг R2RML-star )──► [ Семантический слой OBDA ] ──► [ SPARQL-star отчет ]
   • Таблица проводок (tx)                                • Виртуальный граф                      • Сборка Формы 101
   • Таблица остатков (balances)                          • Вложенные метки времени               • Ризонинг А/П счетов

## 🧱 Шаг 1. Исходные реляционные данные (СУБД банка)

Таблица 2: bank_transactions (Проводки за операционный день)

## 📝 Шаг 2. Описание R2RML-star маппинга
Движок виртуализации (например, Stardog или Ontop) использует расширенный стандарт маппинга, чтобы превратить строки в связи, а метаданные времени (Value/Booking) записать как свойства этих связей в формате RDF-star.
```
@prefix rr:    <http://w3.org> .
@prefix rbo:   <http://example.com> .
@prefix rsb:   <http://w3.org> . # Расширение для RDF-star
@prefix xsd:   <http://w3.org> .

# Маппинг проводки и создание вложенных временных меток для связей
ex:TxMapping a rr:TriplesMap ;
    rr:logicalTable [ rr:tableName "bank_transactions" ] ;
    
    # Субъект — сама транзакция
    rr:subjectMap [ rr:template "http://example.com_{tx_id}" ; rr:class rbo:AccountingEntry ] ;
    
    # Создаем базовую связь Дебета
    rr:predicateObjectMap [
        rr:predicate rbo:hasDebitAccount ;
        rr:objectMap [ rr:template "http://example.com_{dt_acc}" ] ;
    ] ;
    
    # RDF-star расширение: вешаем дату валютирования (Value Date) прямо НА СВЯЗЬ Дебета
    rsb:statementMap [
        rsb:subjectMap [ rr:template "http://example.com_{tx_id}" ] ;
        rsb:predicate rbo:hasDebitAccount ;
        rsb:objectMap [ rr:template "http://example.com_{dt_acc}" ] ;
        
        # Свойства самой связи
        rr:predicateObjectMap [
            rr:predicate rbo:valueDate ;
            rr:objectMap [ rr:column "val_date" ; rr:datatype xsd:date ]
        ] ;
        rr:predicateObjectMap [
            rr:predicate rbo:bookingTimestamp ;
            rr:objectMap [ rr:column "book_time" ; rr:datatype xsd:dateTime ]
        ]
    ] .
```

------------------------------
## 🧮 Шаг 3. Логические правила онтологии для Формы 101
Чтобы отчет автоматически понимал правила Активных и Пассивных счетов при вычислении исходящего остатка, мы закладываем в онтологию логику. На уровне Triple Store работают правила (Rules) или аксиомы:

   1. Определение балансового счета 2-го порядка: Маска из первых 5 цифр 20-значного счета определяет его группу (например, 40817).
   2. Определение валюты: 6, 7 и 8 цифры определяют код валюты (например, 810 или 643).
   3. Формула расчета исходящего баланса ($Bal_{out}$):
   * Для Активных счетов: $Bal_{out} = Bal_{in} + \sum Дт - \sum Кт$
      * Для Пассивных счетов: $Bal_{out} = Bal_{in} + \sum Кт - \sum Дт$
   
------------------------------
## 📊 Шаг 4. Итоговый SPARQL-star запрос для Формы 101
ЦБ требует отчетность по дате проводки (Booking Date). Запрос ниже обращается к семантическому слою, агрегирует входящие остатки на начало месяца (01 августа), собирает все обороты по дебету и кредиту за август, налету определяет тип счета и вычисляет исходящий остаток для Формы 101.
```
PREFIX rbo: <http://example.com>
PREFIX xsd: <http://w3.org>

SELECT ?account5Sign ?currencyCode
       (SUM(?incomingBalance) AS ?InBalance)
       (SUM(?debitTurnover) AS ?DbTurn)
       (SUM(?creditTurnover) AS ?CrTurn)
       (SUM(IF(?accountType = rbo:ActiveAccount, 
            ?incomingBalance + ?debitTurnover - ?creditTurnover, 
            ?incomingBalance + ?creditTurnover - ?debitTurnover)) AS ?OutBalance)
WHERE {
    
    # 1. Извлекаем лицевой счет, определяем его балансовую группу и валюту по маске
    ?account a rbo:BankAccount ;
             rbo:accountNumber ?accNum ;
             rbo:accountType ?accountType . # rbo:ActiveAccount или rbo:PassiveAccount
    
    BIND(SUBSTR(?accNum, 1, 5) AS ?account5Sign)
    BIND(SUBSTR(?accNum, 6, 3) AS ?currencyCode)
    
    # 2. Подтягиваем входящий остаток на начало отчетного периода (Виртуальный маппинг)
    OPTIONAL {
        ?balSnapshot rbo:appliesToAccount ?account ;
                     rbo:balanceDate "2026-08-01"^^xsd:date ;
                     rbo:amountValue ?incomingBalance .
    }
    
    # 3. Собираем ОБОРОТЫ ПО ДЕБЕТУ с использованием RDF-star временного фильтра
    OPTIONAL {
        ?txDb a rbo:AccountingEntry ;
              rbo:amountValue ?debitAmount .
        # Фильтруем дату проводки, которая «зашита» внутри самой связи с помощью RDF-star
        << ?txDb rbo:hasDebitAccount ?account >> rbo:bookingTimestamp ?dbTime .
        FILTER(?dbTime >= "2026-08-01T00:00:00Z"^^xsd:dateTime && ?dbTime <= "2026-08-31T23:59:59Z"^^xsd:dateTime)
    }
    BIND(COALESCE(?debitAmount, 0.0) AS ?debitTurnover)

    # 4. Собираем ОБОРОТЫ ПО КРЕДИТУ с использованием RDF-star временного фильтра
    OPTIONAL {
        ?txCr a rbo:AccountingEntry ;
              rbo:amountValue ?creditAmount .
        # Аналогично вытаскиваем дату проводки для кредитового оборота
        << ?txCr rbo:hasCreditAccount ?account >> rbo:bookingTimestamp ?crTime .
        FILTER(?crTime >= "2026-08-01T00:00:00Z"^^xsd:dateTime && ?crTime <= "2026-08-31T23:59:59Z"^^xsd:dateTime)
    }
    BIND(COALESCE(?creditAmount, 0.0) AS ?creditTurnover)
}
GROUP BY ?account5Sign ?currencyCode
ORDER BY ?account5Sign ?currencyCode
```

## 💎 Преимущества такой реализации для банка

   1. Никаких тяжелых JOIN таблиц по датам: В реляционных базах фильтрация по датам проводок заставляет СУБД сканировать миллионные таблицы индексов. В RDF-star дата проводки является неотемлемой частью дуги графа, связывающей транзакцию и счет. Поиск сужается мгновенно.
   2. Универсальность расчета остатка: Математическая магия SUM(IF(?accountType = ...)) избавляет разработчиков от написания отдельных SQL-процедур для активных (ссудных) и пассивных (депозитных) счетов. Онтология сама знает экономическую суть счета и считает Форму 101 на лету.
   3. Легкость комплаенса: Если ЦБ РФ введет новые пятизначные счета, вам не придется менять логику отчета. Достаточно загрузить в Triple Store обновление справочника Плана счетов, и SPARQL автоматически начнет группировать данные по новым правилам.

## 3

Использование SHACL-star (SHACL*) — это вершина эволюции контроля качества данных в семантических графах. Традиционный стандарт SHACL (Shapes Constraint Language) проверяет структуру узлов (классов) и их свойства. Однако он беспомощен, если нужно проверить ограничение, наложенное на метаданные самой связи (например, проверить дату внутри вложенного триплета RDF-star).
Ниже приведено подробное сравнение того, как валидация критической банковской ошибки («красного сальдо» или нарушения баланса) выглядит в разных стандартах, и готовый пример SHACL-star формы.
------------------------------
## 📊 Сравнение подходов к валидации данных (SHACL vs SHACL-star)

| Критерий сравнения | Классический SHACL (на чистом RDF) | SHACL в рамках Именованных графов (TriG) | SHACL-star (SHACL*) |
|---|---|---|---|
| Что проверяет | Только свойства объектов и связей. Не видит контекст (когда/кем создано). | Проверяет структуру внутри конкретного графа. | Проверяет метаданные связей, условий и вложенных триплетов. |
| Сложность логики | Низкая. Проверить, что у счета 20 знаков — легко. Проверить баланс с учетом даты — сложно. | Высокая. Требуется явное указание ограничений на граф (sh:graph). | Идеальная. Нативно проверяет свойства утверждений («утверждение Х сделано оператором Y»). |
| Избыточность кода | Приходится создавать промежуточные узлы-пустышки для проверки связей. | Требует разделения схем на разные графы. | Минимальный компактный код, повторяющий структуру RDF-star. |
| Сценарий в Форме 101 | Плохо подходит. Не может проверить дату проводки, если она не вынесена в отдельную таблицу. | Подходит для проверки «целостности пакета» (что в документе Дт = Кт). | Идеально. Проверяет, что конкретная проводка на конкретную bookingTimestamp не нарушила правила А/П счетов. |

------------------------------
## 🛠️ Практический пример: Валидация «Красного сальдо»
Бизнес-правило Банка России: Пассивный лицевой счет (например, 40817 — текущий счет гражданина) не может иметь отрицательного остатка («красного сальдо») на конец операционного дня. Если остаток меньше нуля, это критическая ошибка АБС (несанкционированный овердрафт).
Давайте посмотрим, как разные форматы пытаются решить задачу проверки: «Убедиться, что на дату фиксации остатка значение суммы для Пассивного счета строго больше или равно 0».
## 1. Реализация на классическом RDF (Ограниченный подход)
В плоском RDF мы привязаны к узлу «Слепок остатка». Мы не можем привязать дату к факту владения.

# В классическом SHACL мы можем проверить только свойство узла Snapshot
```
ex:PassiveBalanceShape a sh:NodeShape ;
    sh:targetClass rbo:AccountBalanceSnapshot ;
    sh:property [
        sh:path rbo:amountValue ;
        sh:minInclusive 0.0 ; # Сумма должна быть >= 0
        sh:message "Критическая ошибка: Отрицательный остаток на пассивном счете!" ;
    ] .
```
# МИНУС: Форма без разбора заблокирует АКТИВНЫЕ счета (ссудные), где минус — это норма (долг клиента).

## 2. Реализация в формате TriG (Именованные графы)
В TriG мы можем изолировать проверку внутри конкретного операционного дня (графа дня).

# Проверка запускается только внутри графа конкретного дня
```
ex:OperationalDayGraphShape a sh:NodeShape ;
    sh:targetGraph ex:LedgerGraph_2026_08_27 ; 
    # Внутри этого графа ищутся пассивные остатки и проверяются на >= 0
    sh:property [
        sh:path ( rbo:appliesToAccount rbo:amountValue ) ;
        sh:minInclusive 0.0 ;
    ] .
```
# МИНУС: Нам нужно генерировать новые формы валидации или динамически менять targetGraph каждый день.

## 3. Реализация на SHACL-star (Самый мощный и точный вариант)
Спецификация SHACL-star позволяет использовать в качестве пути проверки (sh:path) или мишени (sh:targetSubjectsOf) сами вложенные триплеты.
Мы проверяем не абстрактный узел, а конкретный факт связи счета и его остатка, зафиксированный на определенную дату.
```
@prefix sh:   <http://w3.org> .
@prefix rbo:  <http://example.com> .
@prefix ex:   <http://example.com> .
@prefix xsd:  <http://w3.org> .

# Форма валидации пассивных счетов для Формы 101
ex:PassiveAccountBalanceStarShape a sh:NodeShape ;
    
    # Мишень проверки: все вложенные триплеты, где пассивный счет имеет остаток
    # Пример структуры: << ?account rbo:hasCurrentBalance ?balance >>
    sh:targetObjectsOf rbo:hasCurrentBalance ;

    # Правило 1: Если субъект вложенного триплета — Пассивный счет, 
    # то значение свойства amountValue внутри объекта (?balance) должно быть >= 0
    sh:property [
        sh:path rbo:amountValue ;
        sh:minInclusive 0.0 ;
        sh:message "Регуляторный инцидент ЦБ: Обнаружено красное сальдо на пассивном счете!" ;
    ] ;

    # Правило 2: Проверяем, что дата фиксации этого остатка (внутри вложенного триплета) является валидной датой
    sh:property [
        sh:path rbo:snapshotDate ;
        sh:datatype xsd:date ;
        sh:message "Ошибка метаданных: Отсутствует или некорректна дата операционного дня в RDF-star связи." ;
    ] .
```

## 🚀 Почему SHACL-star побеждает в промышленном банкинге?

   1. Контекстная валидация: Классический SHACL проверяет данные «статично» (как слепок). SHACL-star умеет проверять динамику: он видит метаданные связи. Вы можете написать правило: «Проводка валидна только в том случае, если разница между её bookingTimestamp (временем в системе) и valueDate (временем в экономике) не превышает 48 часов». На обычном SHACL это сделать невозможно без написания тяжелых SPARQL-запросов (sh:sparql).
   2. Экономия ресурсов Triple Store: Ризонеру и валидатору не нужно строить сложные цепочки JOIN через промежуточные узлы реификации. Движок валидации (например, в GraphDB) парсит RDF-star структуру как единый компактный блок, что ускоряет проверку качества данных перед выгрузкой Формы 101 в Центробанк в десятки раз.
   3. Прямой маппинг на бизнес-требования: Инспекторы ЦБ мыслят категориями утверждений: «Операция Х, проведенная сотрудником Y в дату Z». Синтаксис SHACL-star один-в-один повторяет эту бизнес-логику, делая код валидаторов легко читаемым для системных аналитиков банка.

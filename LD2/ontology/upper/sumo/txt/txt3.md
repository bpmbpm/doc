## Рассказ: как Алиса появляется в мире знаний

Представим онтологию SUMO как страну с двумя территориями.

Первая территория — **TBox**, «страна понятий». Здесь живут не конкретные люди и автомобили, а типы, классы, отношения и правила: `Human`, `Automobile`, `Red`, `instance`, `attribute`, `names`. Это мир идей в платоновском смысле: здесь есть образ человека, но нет конкретной Алисы.

Вторая территория — **ABox**, «страна экземпляров». В начальный момент она пуста:

```text
ABox = {}
```

Между ними есть **граница** — место, где система проверяет утверждение, находит нужный класс в TBox, создаёт идентификатор и вносит индивида в ABox.

### Первый шаг: появляется Алиса

Мы пишем:

```lisp
(instance Alice Human)
```

Это SUO-KIF, диалект KIF с Lisp-подобными S-выражениями и префиксной записью: сначала предикат `instance`, затем два аргумента — `Alice` и `Human`. [frontiersin](https://www.frontiersin.org/journals/artificial-intelligence/articles/10.3389/frai.2026.1820380/pdf)

На границе происходит несколько операций.

**1. Анализ предиката.**  
Система видит: `instance` — это отношение между сущностью и классом. Оно означает: «первый аргумент является экземпляром второго аргумента». 

**2. Поиск класса в TBox.**  
Система ищет `Human`. Здесь нужна важная оговорка: искать нужно не «только в ветке Physical», потому что сам класс `Human` в SUMO является элементом системы классов и связан с `Class` через `instance`. Правильнее сказать: система ищет класс `Human`, **экземпляры которого расположены в ветви `Physical`**. 

```lisp
(instance Human Class)
(subclass Human Hominid)
(subclass Human CognitiveAgent)
```

**3. Создание «копии-тени».**  
Это метафора. Система не копирует класс `Human` и не переносит его в ABox. Она создаёт **новый индивид по образцу класса**: не второй `Human`, а конкретного человека, относящегося к `Human`.

По Платону можно сказать: `Human` — эйдос, а `Alice01` — единичная вещь, «тень» или «копия», причастная этому эйдосу. Но в SUMO это не физическое размножение класса, а логический акт инстанцирования.

**4. Учёт на границе: присвоение `id`.**  
В вашей модели системе нужно дать новому индивиду уникальный идентификатор. Назовём его:

```text
Alice01
```

Цифра на конце полезна: она напоминает, что `Alice01` — это не имя «Алиса», а идентификатор конкретного экземпляра. Людей с именем «Алиса» может быть много:

```text
Alice01, Alice02, Alice03, ...
```

**5. Пересечение границы.**  
После проверки ABox пополняется:

```lisp
(instance Alice01 Human)
```

Теперь в «стране экземпляров» есть конкретный физический индивид `Alice01`, относящийся к классу `Human`.

Здесь важна оговорка: в стандартной SUMO `(instance Alice Human)` не «создаёт» человека в физической реальности. Она вводит индивида в **модель базы знаний**. Ваш сценарий корректен, если понимать «создание» как создание записи об индивиде в ABox, а не как материализацию человека в мире.

### Второй шаг: имя Алисы

Мы добавляем:

```lisp
(names "Алиса" Alice01)
```

Здесь через границу перемещается не новый физический индивид, а **абстрактное обозначение**: строка `"Алиса"`.

На границе не создаётся `id` для имени. Вместо этого требуется указать, **куда вписать** это обозначение: к уже существующему `Alice01`.

Это похоже на паспорт. Паспорт — физический документ, но запись «гражданство: Россия» — не новый человек и не новая вещь. Это данные, вписанные в конкретный паспорт. Точно так же `"Алиса"` вписывается в «учётную карточку» `Alice01`:

```text
Alice01
├── класс: Human
└── имя: "Алиса"
```

Формально:

```lisp
(instance Alice01 Human)
(names "Алиса" Alice01)
```

### Третий шаг: возраст

```lisp
(age Alice01 (MeasureFn 16 YearDuration))
```

Через границу перемещается абстрактное значение величины:

```lisp
(MeasureFn 16 YearDuration)
```

Оно означает «16 лет». У этого значения не создаётся отдельного `id` физического экземпляра: `16 лет` — не новая вещь в ABox, а значение, которое вписывается в запись `Alice01`.

```text
Alice01
├── класс: Human
├── имя: "Алиса"
└── возраст: 16 лет
```

Это как запись в паспорте: «дата рождения: …». Дата — не новый человек, а характеристика, привязанная к конкретному человеку.

### Четвёртый шаг: автомобиль

Теперь появляется автомобиль:

```lisp
(instance AliceCar01 Automobile)
(possesses Alice01 AliceCar01)
```

Здесь создаются **два физических индивида**:

- `Alice01` — человек;
- `AliceCar01` — автомобиль.

У каждого свой `id`, потому что это самостоятельные вещи в ABox.

```text
ABox
├── Alice01     — Human
└── AliceCar01  — Automobile
```

Затем фиксируется отношение владения:

```text
Alice01 ── possesses ──> AliceCar01
```

### Пятый шаг: цвет автомобиля

```lisp
(attribute AliceCar01 Red)
```

Здесь через границу перемещается абстрактное значение атрибута `Red`.

На границе не создаётся `RedCar01` и не создаётся новый физический индивид. Система должна указать, **в чью запись вписать свойство**:

```text
AliceCar01
├── класс: Automobile
└── цвет: Red
```

Формально:

```lisp
(instance AliceCar01 Automobile)
(attribute AliceCar01 Red)
```

`Red` — значение атрибута из абстрактной ветви:

```text
Entity
└── Abstract
    └── Attribute
        └── ColorAttribute
            └── Red
```

Автомобиль же находится в физической ветви:

```text
Entity
└── Physical
    └── Object
        └── ... → Vehicle → Automobile → AliceCar01
```

## Комментарии к трактовке

### Что в сценарии верно

- Разделение TBox и ABox точно отражает различие между **схемой понятий** и **фактами о конкретных индивидах**.
- Идея границы хорошо объясняет проверку типов, доменов и диапазонов.
- Идентификатор `Alice01` полезен, чтобы отличать индивида от имени «Алиса».
- Паспортная метафора удачна для `attribute`, `age` и `names`: данные вписываются в запись уже существующего индивида.
- Платоновские «копия» и «тень» хорошо передают интуицию: класс — образец, индивид — конкретное проявление.

### Что нужно поправить

1. **Класс не копируется в ABox.**  
   `Human` остаётся в TBox. В ABox появляется `Alice01`, связанный с `Human` через `instance`.

2. **`Human` не находится в ветви `Physical` как класс.**  
   Физическими являются экземпляры `Human`, например `Alice01`. Сам `Human` — класс и экземпляр `Class`.

3. **`instance` не создаёт физический объект в реальности.**  
   Он вводит индивида в модель ABox. Реальный человек не появляется от того, что мы написали формулу.

4. **Для свойств `id` действительно не нужен, но нужен носитель.**  
   `Red` не становится отдельной вещью; оно приписывается `AliceCar01` через `attribute`.

5. **Имя — не свойство в смысле `attribute`.**  
   В SUMO для имени есть отдельное отношение `names`. Его можно образно назвать «записью в паспорте», но формально это не `attribute`.

## Готовый мини-сценарий

```lisp
;; TBox уже содержит понятия:
;; Human, Automobile, Red, names, age, attribute, possesses

;; 1. Через границу создаётся физический индивид
(instance Alice01 Human)

;; 2. В его «паспорт» вписывается имя
(names "Алиса" Alice01)

;; 3. В его «паспорт» вписывается возраст
(age Alice01 (MeasureFn 16 YearDuration))

;; 4. Создаётся ещё один физический индивид — автомобиль
(instance AliceCar01 Automobile)

;; 5. Фиксируется отношение владения
(possesses Alice01 AliceCar01)

;; 6. В «паспорт автомобиля» вписывается цвет
(attribute AliceCar01 Red)
```

Итоговое состояние ABox:

```text
Alice01
├── instance: Human
├── names: "Алиса"
└── age: 16 лет

AliceCar01
├── instance: Automobile
├── attribute: Red
└── владелец: Alice01
```

## Как развить аналогию

Эта история хорошо подходит для популярного объяснения семантических технологий:

- **TBox** — словарь и правила языка: что вообще может существовать и как понятия связаны.
- **ABox** — конкретные записи: кто именно существует, что у него есть и какими свойствами он обладает.
- **Граница** — валидатор: он не даёт вписать «красный» вместо человека или приписать свойство несуществующему `id`.
- **`id`** — уникальный номер записи, а не имя и не сама вещь.
- **`instance`** — «завести карточку нового объекта».
- **`attribute`** — «вписать характеристику в уже заведённую карточку».
- **`names`** — «указать, как эту карточку называют словами».

Тогда семантическая технология — это не просто база данных, а система, где каждая запись связана с формально определёнными понятиями и правилами. Благодаря этому машина может не только хранить `Alice01`, `"Алиса"` и `Red`, но и понимать: Алиса — человек, у неё есть автомобиль, автомобиль красный, а красный — это цвет. ## 2. Полная ветвь `Human` в `Physical`

В SUMO `Human` — один класс с двумя суперклассами:

```lisp
(subclass Human Hominid)
(subclass Human CognitiveAgent)
```



Обе ветви ведут в `Physical`:

```text
Entity
└── Physical
    ├── Object
    │   └── CorpuscularObject
    │       └── OrganicObject
    │           └── Organism
    │               └── Animal
    │                   └── Vertebrate
    │                       └── Mammal
    │                           └── Primate
    │                               └── Hominid
    │                                   └── Human
    │
    └── Object
        └── CorpuscularObject
            └── Agent
                └── SentientAgent
                    └── CognitiveAgent
                        └── Human
```

Точная промежуточная цепочка может немного отличаться между версиями SUMO, но принцип устойчив: **оба родителя `Human` находятся под `Object`, а `Object` — под `Physical`**. Поэтому любой экземпляр `Human` — физический индивид. 

Важно: это не «два `Human`». Это **один `Human` с двумя путями наследования**:

```text
Human → Hominid → ... → Physical
Human → CognitiveAgent → ... → Physical
```

## 3. Граница: учёт, а не копирование

Согласен: формулировку «на границе создаётся копия `Human`» нужно убрать. Класс `Human` находится в TBox; на границе его нет, и копировать его туда не нужно.

Более точный конвейер:

```text
TBox: Human — образ / универсалия
  ↓
Граница: анализ утверждения, проверка класса, маркировка нового id
  ↓
ABox: Alice01 — конкретная запись о физическом экземпляре
```

На границе происходит:

1. Читается утверждение `(instance Alice Human)`.
2. Проверяется, что `Human` существует в TBox как класс.
3. Создаётся уникальная метка / идентификатор `Alice01`.
4. В ABox фиксируется связь: `Alice01` — экземпляр `Human`.

То есть граница — не «копировальный цех», а **участок маркировки и регистрации**: поступает заявка «создать экземпляр Human», контролёр проверяет образец в каталоге TBox, выдаёт номер `Alice01` и отправляет запись в ABox.

Метафора конвейера действительно лучше паспортного контроля:

```text
TBox — каталог форм и образцов
Граница — участок маркировки и регистрации
ABox — склад готовых учётных карточек
```

## 4. Четыре области

Ваша четырёхчастная модель хорошо передаёт эпистемологическую сторону: человек знает о «мире вещей» только через созданную им базу знаний.

| Область | Что в ней находится | Пример |
|---|---|---|
| **Мир идей / TBox** | Классы, отношения, правила: `Human`, `Automobile`, `Red`, `instance` | «Человек — это…» |
| **Граница** | Проверка, маркировка, присвоение `id`, фиксация связи | `Alice01` получает статус экземпляра `Human` |
| **Мир вещей в сознании / ABox** | Знания человека о конкретных индивидах | «`Alice01` — Human; у неё есть автомобиль» |
| **Полный мир вещей** | Реальность вне модели: реальные люди, автомобили, события | Реальная Алиса и её реальный автомобиль |

Формально:

```text
Знание человека о мире вещей = TBox + ABox
```

Но это знание — **модель**, а не сам полный мир вещей. ABox может содержать `Alice01`, тогда как в полном мире вещей может существовать много реальных Алис; и наоборот, в ABox могут быть записи о том, чего в реальности нет.

## 5. Возраст: более простая запись

Согласен: `(MeasureFn 16 YearDuration)` технически точно, но для вводного рассказа слишком тяжело. Можно использовать качественный атрибут:

```lisp
(attribute Alice01 YoungAdult)
```

Или, если нужен простой русский смысл:

```lisp
(attribute Alice01 Young)
```

Здесь `Young` или `YoungAdult` — значение атрибута из абстрактной ветви. Это не создаёт новый физический индивид, а вписывает характеристику в «карточку» `Alice01`:

```text
Alice01
├── instance: Human
├── names: "Алиса"
└── attribute: YoungAdult
```

Точная формальная запись возраста остаётся полезной для измерений, но для популярного объяснения лучше начать с `attribute`.

## 6. `Human` и `Physical`: уточнение

Ваша формулировка верна, если говорить о **классификации экземпляров**:

```text
Human находится в Physical-ветви через обоих родителей:
Hominid и CognitiveAgent.
```

Но нужно различать два утверждения:

```lisp
(instance Human Class)      ; Human — класс
(subclass Human Hominid)    ; Human — подкласс Hominid
(subclass Human CognitiveAgent) ; Human — подкласс CognitiveAgent
```

Поэтому корректно говорить:

> **`Human` — класс, оба пути наследования которого ведут к `Physical`; следовательно, все его экземпляры физичны.**

Но неправильно говорить:

> **`Human` — физический индивид.**

`Human` — не конкретный человек, а тип. Физическим индивидом является `Alice01`.

## 7. Имя: почему это не `attribute`

`names` находится в системе отношений, а не в ветви `Attribute`. Разница такая:

```lisp
(attribute AliceCar01 Red)      ; автомобиль обладает цветом
(names "Алиса" Alice01)         ; строка является именем человека
```

`Red` — **атрибут**: качество, которое может быть у объекта.

`"Алиса"` — **обозначение**: языковый знак, который указывает на `Alice01`.

Иерархия для `Red`:

```text
Entity
└── Abstract
    └── Attribute
        └── ColorAttribute
            └── Red
```

А `names` — это не значение качества, а **отношение между языковым выражением и сущностью**:

```text
"Алиса" ── names ──> Alice01
```

Поэтому имя можно назвать «свойством записи» в бытовом смысле, но в SUMO это не `Attribute`. Это **языковая привязка**: не «Алиса красная», а «Алиса называется “Алиса”».

Если очень нужна единая метафора паспорта, то:

- `attribute AliceCar01 Red` — графа «цвет» в паспорте автомобиля;
- `names "Алиса" Alice01` — графа «имя» в паспорте человека;
- но формально это разные типы отношений: первый — качество, второй — обозначение.

## Исправленный рассказ

```lisp
;; TBox: образ человека
;; Human → Hominid → ... → Physical
;; Human → CognitiveAgent → ... → Physical

;; На границе:
;; 1. читаем заявку
;; 2. проверяем образ Human в TBox
;; 3. выдаём маркировку Alice01
;; 4. регистрируем экземпляр в ABox

(instance Alice01 Human)

;; В ABox появляется физический индивид Alice01.
;; Он наследует обе ветви Human:
;; биологическую и агентную.

;; Вписываем обозначение в карточку Alice01.
(names "Алиса" Alice01)

;; Вписываем качественную характеристику.
(attribute Alice01 YoungAdult)

;; Создаём ещё один физический индивид.
(instance AliceCar01 Automobile)

;; Связываем два физических индивида отношением владения.
(possesses Alice01 AliceCar01)

;; Вписываем абстрактное свойство в карточку автомобиля.
(attribute AliceCar01 Red)
```

Итог:

```text
TBox
Human, Automobile, Red, YoungAdult,
instance, names, attribute, possesses

Граница
Alice01 ← маркировка нового экземпляра Human
AliceCar01 ← маркировка нового экземпляра Automobile

ABox
Alice01 ── instance ──> Human
Alice01 ── names ──> "Алиса"
Alice01 ── attribute ──> YoungAdult
AliceCar01 ── instance ──> Automobile
AliceCar01 ── attribute ──> Red
Alice01 ── possesses ──> AliceCar01
```

## Главная поправка

> **Граница не копирует `Human` и не создаёт его копию. Она проверяет образ в TBox, выдаёт уникальную маркировку `Alice01` и регистрирует в ABox факт: `Alice01` — экземпляр `Human`.**  
> **Для абстрактных характеристик маркировка нового физического индивида не создаётся: создаётся или выбирается значение, которое привязывается к уже существующему `id` через `attribute` или `names`.**


## 2.1

Коротко: **`Young` и `YoungAdult` не являются стандартными базовыми классами `Merge.kif` в том виде, в каком я их использовал ранее**. Для популярного примера лучше не inventировать термин, а использовать проверяемый SUMO-атрибут, например `Female`/`Male` — либо явно объявить `YoungAdult` как собственное расширение. Для `names` ветвь иная: это не класс-атрибут, а **бинарное отношение**; его «иерархия» — это иерархия отношений, а не ветвь `Attribute`. [arxiv](https://arxiv.org/pdf/2012.15835.pdf)

## 1. `Young` и `YoungAdult`

Я должен исправить предыдущий пример: нельзя уверенно утверждать, что в текущем `Merge.kif` есть готовые классы `Young` или `YoungAdult` с такими цепочками наследования. В SUMO возраст обычно моделируют не одним словом-атрибутом, а через измерение:

```lisp
(age Alice01 (MeasureFn 16 YearDuration))
```

Это сложнее, но онтологически точнее: возраст — величина, а не просто ярлык.

Если вам нужен простой «атомарный» ярлык, его следует объявить самостоятельно:

```lisp
(subclass YoungAdult Human)

(documentation YoungAdult
"Человек, находящийся в раннем взрослом возрасте.")

(instance Alice01 YoungAdult)
```

Тогда иерархия будет такой:

```text
Entity
└── Physical
    └── Object
        └── ... → Organism → Hominid → Human → YoungAdult → Alice01
```

И параллельно, через второго родителя `Human`:

```text
Entity
└── Physical
    └── Object
        └── ... → Agent → CognitiveAgent → Human → YoungAdult → Alice01
```

**Перевод:** `Alice01` — молодой взрослый человек; она наследует и биологическую, и агентную ветви `Human`.

Но это уже **ваше расширение SUMO**, а не готовый термин базового `Merge.kif`.

### Лучше для базовой SUMO

Если не хочется вводить собственный класс, используйте измерение:

```lisp
(age Alice01 (MeasureFn 16 YearDuration))
```

Перевод:

> **Возраст `Alice01` равен 16 годам.**

Здесь `16` — число, `YearDuration` — единица измерения года, а `(MeasureFn 16 YearDuration)` — конкретное значение длительности.

## 2. Полная ветвь `names`

`names` — это не класс и не атрибут. Это **бинарное отношение** (предикат), связывающее символьную строку и сущность.

```lisp
(names "Алиса" Alice01)
```

Читается:

> **Строка “Алиса” является именем `Alice01`.**

Его место в SUMO можно показать так:

```text
Entity
└── Abstract
    └── Relation
        └── Predicate
            └── BinaryRelation
                └── names
```

То есть `names` — не значение свойства, а **правило связи**: оно соединяет два аргумента.

```text
"Алиса" ── names ──> Alice01
```

### Аргументы `names`

```lisp
(names ?STRING ?ENTITY)
```

| Позиция | Тип | Пример |
|---|---|---|
| 1 | `SymbolicString` | `"Алиса"` |
| 2 | `Entity` | `Alice01` |

`SymbolicString` — класс символьных/алфавитно-цифровых последовательностей; он относится к абстрактной части онтологии. [ontology.nps](https://ontology.nps.edu/sigma/TreeView.jsp?lang=EnglishLanguage&simple=yes&kb=SUMO&file=domainEnglishFormat.kif&line=13578)

Поэтому `Alice01` стоит вторым не потому, что он «менее важен», а потому что так определён предикат:

```text
names(имя, тот, кого называют)
```

Если хочется привычного порядка «объект — имя», можно определить собственное отношение:

```lisp
(instance hasName BinaryRelation)

(domain hasName 1 Entity)
(domain hasName 2 SymbolicString)

(=>
  (hasName ?X ?S)
  (names ?S ?X))
```

Тогда можно писать:

```lisp
(hasName Alice01 "Алиса")
```

Но это уже пользовательское расширение SUMO, а не стандартный предикат.

## 3. Как отличить `names`, `attribute` и `instance`

| Предикат | Что связывает | Пример | Ветвь второго аргумента |
|---|---|---|---|
| `instance` | Индивид и класс | `(instance Alice01 Human)` | `Class` |
| `attribute` | Индивид и значение атрибута | `(attribute AliceCar01 Red)` | `Attribute` |
| `names` | Строку и сущность | `(names "Алиса" Alice01)` | `Entity` |
| `age` | Индивид и длительность | `(age Alice01 (MeasureFn 16 YearDuration))` | `TimeDuration` |
| `possesses` | Агента и объект | `(possesses Alice01 AliceCar01)` | `Object` |

Поэтому:

```lisp
(attribute Alice01 YoungAdult)   ; только если YoungAdult объявлен как Attribute
(instance Alice01 YoungAdult)    ; если YoungAdult объявлен как подкласс Human
(names "Алиса" Alice01)          ; стандартная SUMO-запись имени
```

В моём предыдущем примере `(attribute Alice01 YoungAdult)` был неудачен, если `YoungAdult` вводится как подкласс `Human`. Тогда правильно:

```lisp
(instance Alice01 YoungAdult)
```

## 4. Проверяемый простой пример без новых терминов

Чтобы не добавлять `YoungAdult`, можно построить рассказ так:

```lisp
;; 1. На границе создаётся и маркируется физический индивид
(instance Alice01 Human)

;; 2. В карточку Alice01 вписывается имя
(names "Алиса" Alice01)

;; 3. В карточку вписывается измеряемая характеристика
(age Alice01 (MeasureFn 16 YearDuration))

;; 4. Создаётся второй физический индивид
(instance AliceCar01 Automobile)

;; 5. Фиксируется отношение владения
(possesses Alice01 AliceCar01)

;; 6. В карточку автомобиля вписывается абстрактное значение цвета
(attribute AliceCar01 Red)
```

## 5. Итоговая схема

```text
TBox — мир идей
├── Human
│   ├── Hominid → ... → Physical
│   └── CognitiveAgent → ... → Physical
├── Automobile → ... → Physical
├── Red → ColorAttribute → Attribute → Abstract
├── names → BinaryRelation → Predicate → Relation → Abstract
└── age → BinaryRelation → Predicate → Relation → Abstract

Граница — маркировка и регистрация
├── Alice01 получает id и связь с Human
└── AliceCar01 получает id и связь с Automobile

ABox — мир вещей в сознании
├── Alice01 ── instance ──> Human
├── "Алиса" ── names ──> Alice01
├── Alice01 ── age ──> 16 лет
├── AliceCar01 ── instance ──> Automobile
├── AliceCar01 ── attribute ──> Red
└── Alice01 ── possesses ──> AliceCar01
```

## Главная поправка

> **`Young` / `YoungAdult` не следует подавать как готовые базовые термины SUMO без проверки конкретной версии. Для возраста корректнее использовать `(age Alice01 (MeasureFn 16 YearDuration))`; для простого ярлыка нужно объявить собственный класс или атрибут.**  
> **`names` — не ветвь `Attribute`, а бинарное отношение: `(names "Алиса" Alice01)` связывает строку-имя с индивидом `Alice01`.** [arxiv](https://arxiv.org/pdf/2012.15835.pdf)
